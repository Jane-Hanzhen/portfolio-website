## 1. 项目概览

### 1.1 项目名称

**UrbanInsight AI｜AI 驱动的城市潜力分析与决策支持平台**

### 1.2 一句话定位

基于伦敦 33 个行政区的多维城市指标与 PCA–TOPSIS 综合评价模型，设计并实现一个以地图为入口、由 AI 辅助解释的城市潜力分析平台，将专业统计结果转化为可探索、可解释、可比较、可输出报告的决策信息。

### 1.3 项目本质

该项目不是“先做了一个城市评价模型，后来又给它加了网页”，而是将原有的城市潜力评价与归因分析能力产品化：

1. 用多源、多维城市指标建立统一的数据基础；
2. 用确定性的统计分析引擎完成降维赋权、综合评分、排名与贡献度计算；
3. 用地图和可视化降低城市空间分析的理解门槛；
4. 用 AI 将结构化结果解释为区域优势、短板、对比结论与发展建议；
5. 用结构化输出与报告能力支持进一步的决策沟通。

因此，它可以被定义为一个完整的 **AI + 数据模型 + GIS 可视化 + 决策支持产品**。

### 1.4 项目背景

传统城市潜力分析通常需要分析人员分别完成数据搜集、指标处理、统计建模、地图制图、结论归纳和报告撰写。其主要问题包括：

- 多源城市数据分散，字段、尺度和口径不统一；
- PCA、TOPSIS 等分析方法具有专业门槛；
- 综合评分能够说明“结果如何”，却不容易直接解释“为什么”；
- 区域指标、地图空间位置和模型贡献度分散在不同分析载体中；
- 跨区域比较及报告整理依赖人工操作，流程较长；
- 传统 Dashboard 容易形成信息密集的指标墙，不利于非专业用户理解。

UrbanInsight AI 尝试将上述流程整合为一条连续的产品体验，让用户从选择行政区开始，经由地图、统计结果与 AI 解释逐步完成分析。

### 1.5 项目时间与组织方式

- **原城市生活质量评价研究**：2024.11–2025.01，三人小组项目，本人担任负责人；
- **网页与 AI 平台化阶段**：2026.06，约 1 个月，由本人独立完成。

两个阶段不是两个互不相关的项目：前一阶段建立数据、指标体系与 PCA 空间分析基础，后一阶段将其重构为可重复运行、可视化和可由 AI 辅助解释的分析产品。

## 2. 产品定位与目标用户

### 2.1 产品定位

UrbanInsight AI 是面向伦敦行政区的 AI 辅助城市潜力分析平台。产品强调：

- **Map-first**：地图是首次探索和区域选择的核心入口；
- **AI-guided**：AI 贯穿分析过程，但不替代统计计算；
- **Progressive disclosure**：选择区域后再逐层展示数据、评分和洞察；
- **Decision-ready**：输出不止于数据展示，还包括对比、建议和报告；
- **Explainable**：评分、贡献度和 AI 解释均建立在可追溯的数据库结果之上。

### 2.2 目标用户

现有产品规范中的目标用户包括：

- 城市规划人员；
- 政府及公共部门分析人员；
- 城市与区域研究人员；
- 学生与研究型用户；
- 商业分析及区域研究人员。

从应用场景进一步延伸，也可服务于选址研究、城市咨询和区域发展评估，但这三类尚属于合理应用方向，不应在没有实际案例时写成已验证用户。

### 2.3 用户核心任务

- 快速查找并选择伦敦行政区；
- 理解某一区域的综合潜力评分和伦敦范围内排名；
- 查看经济、社会、生态三个维度的表现；
- 识别影响区域表现的主要指标和贡献因素；
- 通过自然语言追问评分差异与发展原因；
- 对比两个行政区的优势、短板和指标差异；
- 生成结构化 Markdown 分析报告。

### 3.1 产品目标

- 降低城市综合评价模型的使用和理解门槛；
- 让区域评分从“静态结果”升级为“可解释的分析过程”；

- 通过 Mock AI 模式支持无模型成本的产品开发与测试。

| 数据与结果分散 | 统一通过 SQLite、FastAPI 和前端分析工作区呈现 |

## 4. 数据基础与指标体系

### 4.1 数据覆盖

当前 Version 1 覆盖：

- **33 个伦敦行政区**；
- **每区 12 项处理后指标**；
- **经济、社会、生态 3 个维度**；
- 33 条行政区记录、33 条指标记录和 33 条分析结果记录为预期完整状态。

12 项指标分别为：

| 维度 | 指标 | 含义 / 计算口径 | 方向 |
|---|---|---|---|
| 经济 | 人均可支配收入 | GDHI per capita | 正向 |
| 经济 | 企业密度 | 每千人企业数量 | 正向 |
| 经济 | 房价收入比 | 平均房价 / 收入 | 负向；平台计算时进行正向化 |
| 社会 | 公交站点密度 | 行政区内交通站点点密度均值 | 正向 |
| 社会 | 医疗设施密度 | 医院、药房等 POI 点密度均值 | 正向 |
| 社会 | 警务设施密度 | 警务 POI 点密度均值 | 正向 |
| 社会 | 文化设施密度 | 文化设施 POI 点密度均值 | 正向 |
| 社会 | 便民服务密度 | 便民设施 POI 点密度均值 | 正向 |
| 生态 | 生活垃圾回收率 | Household waste recycling rate | 正向 |
| 生态 | NDVI | Landsat 影像计算的植被指数均值 | 正向 |
| 生态 | WET | Landsat 影像计算的湿度指标均值 | 正向 |
| 生态 | 综合景观指数 | 土地利用景观格局综合指标 | 正向 |

### 4.2 原项目分析基础

早期项目“城市潜力评价体系构建与归因分析”已经形成以下方法基础：

- 融合遥感、POI、政府统计、土地利用与行政区边界等多源数据；
- 使用 Python 与 ArcGIS 构建多维综合评价矩阵；
- 采用经济、社会、生态三个准则层及 12 个细分指标；
- 使用 SPSS 完成 PCA 适用性检验、主成分提取和 UQI 计算；
- 使用 R 完成 Global Moran’s I、LISA 与 Getis-Ord Gi* 热点分析；
- 通过主成分载荷和空间格局解释行政区差异。

这部分不是与 UrbanInsight AI 平行的旧项目，而是平台分析模型与数据产品能力的前身。

需要准确区分两个阶段：原始小组报告没有使用 TOPSIS；PCA 加权 TOPSIS、贡献度持久化与 AI 解释属于 2026 年平台化阶段的重构。

### 4.3 数据管线

运行时数据链路为：

```text
原始/整理后 CSV
→ 导入脚本
→ 字段及数值校验
→ SQLite indicators
→ PCA–TOPSIS 分析引擎
→ SQLite analysis_results
→ FastAPI
→ 地图、图表与 AI 分析
```

CSV 是导入来源，不在用户使用平台时被直接查询。浏览器与 AI 均不能直接读取 CSV。

### 4.4 数据存储

SQLite 包含三张核心表：

- `boroughs`：行政区 ID、名称、London 区域标识和 GeoJSON 几何引用；
- `indicators`：每个行政区的 12 项处理后指标；
- `analysis_results`：综合评分、排名、三维度得分、贡献度与 PCA 元数据。

行政区编码是连接 GeoJSON、指标数据、模型结果和 AI 请求的稳定主键。

### 4.5 待补充的数据事实

原始报告能够确认：

- POI：OpenStreetMap / Overpass Turbo，包含交通、医疗、文化、警务和便民服务五类，共 **29,087 个点**；
- 土地利用：ESRI，10m 分辨率；
- 遥感：USGS Landsat 8 OLI-TIRS，30m 分辨率；
- 统计数据：London Datastore 与 ONS，按 London Borough 汇总；
- 行政区边界：UK Data Service；
- 除行政区边界采用 2011 年版本外，其余数据为 2022 年；
- POI 先裁剪至伦敦边界，再进行点密度分析并计算各行政区均值；
- Landsat 影像进行了几何校正、大气校正与边界裁剪；
- 土地利用数据重分类为 Water、Trees、Flooded Vegetation、Crops、Built Area、Bare Ground、Snow/Ice 和 Rangeland。

仍待从源数据或代码补充：缺失值与异常值处理规则、平台标准化的精确公式、各统计指标的单位元数据、更新频率及清洗前后的完整记录数。

原始报告未将 AQI 纳入最终 12 项指标，因此简历不应继续写“融合 AQI”，除非后续能提供实际参与建模的证据。

## 5. 统计分析模型

### 5.1 模型定位

分析引擎是平台唯一的数学计算来源。大型语言模型不参与 PCA、TOPSIS、评分或排名计算，确保相同数据能够得到稳定、可复现的结果。

### 5.2 分析流程

Python + NumPy 分析引擎负责：

1. 从 SQLite 读取全部行政区指标；
2. 校验评价矩阵；
3. 对指标进行标准化；
4. 拟合 PCA；
5. 根据 PCA 结果计算指标权重；
6. 运行 TOPSIS；
7. 计算行政区综合得分；
8. 生成顺序排名；
9. 计算经济、社会、生态维度得分；
10. 计算指标及维度贡献度；
11. 将结果持久化至 SQLite。

### 5.3 原研究与平台模型的演进

原研究先进行 KMO 与 Bartlett 检验：KMO 为 **0.789**，Bartlett 球形检验显著性为 **0.000**，说明指标适合 PCA。最终保留 4 个主成分，累计解释方差为 **91.125%**，并使用各主成分贡献率加权计算 UQI。

平台化阶段保留 PCA 的客观降维与赋权思想，并进一步接入 TOPSIS：以标准化后的加权指标矩阵确定正、负理想解，计算各行政区到两类理想解的距离，再得到相对贴近度、综合得分与排名。具体实现公式应以最终分析引擎代码为准，在代码复核前不写入更细的归一化口径。

### 5.4 运行机制

分析引擎通过后端脚本显式运行，而不是用户每点击一个行政区就重新计算。前端选择区域时读取已经持久化的分析结果。

这种设计实现了：

- 统计结果稳定；
- 用户交互响应更快；
- AI 无权修改评分；
- 计算层与解释层可以独立测试；
- 数据更新后可统一重新分析，避免不同用户得到不一致结果。

### 5.5 可解释性设计

平台不仅保存综合分数和排名，还保存：

- 经济、社会、生态三个维度的得分；
- 指标贡献度；
- 维度贡献度；
- PCA 相关元数据。

AI 的作用是将这些确定性结果组织为自然语言洞察，而不是在无法追溯的情况下直接给出判断。

## 6. 核心功能

### 6.1 地图探索与行政区选择

- 使用 MapLibre GL JS 加载本地伦敦行政区 GeoJSON；
- 支持行政区悬停预览、Tooltip、发光高亮；
- 点击行政区后突出目标区域并弱化其他区域；
- 自动调整地图视野以适配所选区域；
- Home 控件恢复伦敦默认视角，但保留当前分析状态；
- GeoJSON 缺失时保留地图外壳并展示本地化错误状态，不导致页面崩溃。

### 6.2 行政区搜索

- 支持不区分大小写的子字符串搜索；
- 最多显示 6 个结果；
- 支持 Enter 选择首项、Escape 关闭结果；
- 搜索选择与地图点击触发相同分析流程；
- 搜索框与当前选择区域保持同步。

### 6.3 AI 分析面板

AI Panel 包含五类状态：

- `idle`：解释 UrbanInsight AI 的能力和使用方式；
- `hover`：预览当前悬停区域并邀请用户选择；
- `selected`：确认区域选择；
- `analyzing`：展示五步分析进度；
- `completed`：显示区域、综合分数、排名及后续交互。

它不是孤立聊天框，而是连接地图选择、分析进度、结果摘要、多轮追问和区域比较的上下文助手。

### 6.4 分析工作区

区域分析完成后，页面下方出现 Analysis Workspace，包括：

- 行政区名称与报告操作；
- 综合评分、伦敦范围排名和摘要；
- 经济、社会、生态三维度卡片；
- 三维度雷达图；
- 贡献度横向条形图；
- 12 项指标卡片；
- 主要驱动因素与指标解释；
- 优势、短板和建议；
- Markdown 报告导出。

### 6.5 AI 多轮追问

分析完成且已知行政区 ID 后，用户可以继续提问。后端将当前行政区、权威分析上下文和必要的历史上下文一并提供给模型，使回答围绕当前分析继续展开。

现阶段对话上下文由请求携带，不持久化到数据库，因此刷新或新会话后不能恢复历史对话。

### 6.6 行政区比较

用户可以选择第二个行政区进行比较。系统为两个区域分别构建完整上下文，AI 解释：

- 已提供的评分差异；
- 指标差异；
- 贡献度差异；
- 相对优势；
- 发展缺口。

AI 不重新计算或生成新的评分和排名。

### 6.7 报告生成

系统可以生成 Markdown 报告，规范包含：

- Executive Summary；
- Regional Evaluation；
- Key Indicators；
- Strengths；
- Weaknesses；
- Recommendations。

前端将返回文本转换为 `.md` 文件下载。当前未实现 PDF 报告。

### 6.8 国际化与响应式

- 支持 `en` 与 `zh-CN`；
- 中文浏览器默认使用简体中文，其他语言默认英文；
- 用户语言偏好保存至 `localStorage`；
- 指标名称通过稳定 ID 翻译；
- 官方行政区名称、数据库 ID、数值和 JSON 字段不被翻译；
- 桌面端采用地图与 AI 面板 7:3 布局；
- 小于 1024px 后改为纵向堆叠；
- 移动端保留地图、面板、卡片和操作的可用布局。

## 8. AI 能力与实现

### 8.1 AI 在产品中的角色

AI 被定位为“城市分析助手”，承担：

- 解释模型评分及排名；
- 识别关键驱动因素；
- 解释指标及贡献度；
- 总结区域优势与短板；
- 生成发展建议；
- 回答上下文相关追问；
- 对比两个行政区；
- 生成结构化报告。

AI 不承担：

- PCA 与 TOPSIS 计算；
- 自行生成区域评分；
- 修改数据库结果；
- 独立创造区域排名；
- 补充数据库中不存在的指标事实。

### 8.2 AI 架构

后端 AI 模块包含：

- **Context Builder**：从数据库读取并组织行政区、指标、统计结果和贡献度；
- **Prompt Builder**：根据分析、追问、比较和报告任务生成约束化 Prompt；
- **Response Schema**：验证结构化分析结果；
- **Provider Strategy**：隔离不同模型提供方；
- **Mock Provider**：在不调用外部模型的情况下返回可用的仿真结果。

### 8.3 模型与运行模式

系统支持两种模式：

- `mock`：用于 UI 开发、联调与无成本测试；
- `live`：调用真实模型服务。

支持的模型提供方：

- OpenAI；
- Qwen（阿里云 DashScope OpenAI-compatible 接口）；
- DeepSeek。

前端不知道当前使用哪一个 Provider，只依赖统一的后端响应契约。

已完成真实端到端调用的模型：

- **Qwen：qwen3.7-plus**；
- **DeepSeek：deepseek-v4-flash**。

OpenAI Provider 与配置已实现，但由于未充值 API Key，尚未完成有效的真实回答验证，因此不能写成“已验证 OpenAI 效果”。Westminster Markdown 报告由 `deepseek-v4-flash` 真实生成，可作为端到端链路证据。

### 8.4 结构化输出

初始分析接口返回经过 Schema 验证的 `AnalysisInsights`，用于稳定渲染：

- 摘要；
- 主要驱动因素；
- 指标解释；
- 优势；
- 短板；
- 建议及优先级。

报告接口返回 Markdown，追问和比较接口返回文本。非法 JSON 或结构不符合预期时，由后端识别并转化为统一错误，而不是直接把异常内容展示给用户。

### 8.5 防幻觉与可信性设计

平台通过以下机制降低幻觉：

1. **计算与解释分离**：统计计算仅由 Python 引擎执行；
2. **数据库为唯一事实源**：AI 只接收 Context Builder 提供的数据；
3. **明确能力边界**：Prompt 禁止 AI 自行生成评分、排名和缺失指标；
4. **稳定字段契约**：指标 ID、行政区 ID、数值和优先级枚举保持不变；
5. **结构化验证**：分析结果必须符合 Pydantic/响应 Schema；
6. **错误兜底**：AI 失败时仍然显示确定性的统计结果；
7. **Provider 解耦**：替换模型不会改变前端业务逻辑；
8. **Mock 测试**：可独立验证产品流程，不依赖付费模型或不稳定网络。

这套机制比“直接把数据库内容拼进 Prompt 后让模型自由回答”更可控，也使产品更适用于需要解释性和一致性的专业场景。

### 8.6 AI 异常与安全

- 缺少所选 Provider 的 API Key：返回服务不可用；
- 不支持的运行模式或 Provider：返回服务不可用；
- 外部模型 API 或解析异常：前端获得通用错误，后端记录脱敏日志；
- 日志会过滤已配置 Key 和常见 `sk-...` 模式；
- Key 仅保存在 `backend/.env`；
- Key 不进入前端变量、不通过状态接口返回、不写入浏览器日志。

## 9. 系统架构

### 9.1 技术栈

| 层级 | 技术 | 主要职责 |
|---|---|---|
| 前端 | React、TypeScript、Vite、Tailwind CSS | 页面状态、地图、AI 面板、分析工作区、双语及响应式 |
| 地图 | MapLibre GL JS、GeoJSON | 行政区探索、选择、空间高亮和相机交互 |
| 图表 | Recharts | 雷达图与贡献度条形图 |
| 后端 | Python、FastAPI、Pydantic | REST API、数据访问、AI 编排、校验与错误映射 |
| 数据库 | SQLite | 行政区、指标、分析结果和模型元数据 |
| 分析 | NumPy、PCA–TOPSIS | 标准化、权重、评分、排名与贡献度 |
| AI | OpenAI SDK / OpenAI-compatible APIs | 结果解释、追问、比较与报告 |

### 9.2 架构原则

```text
用户
↓
React + TypeScript 前端
↓
FastAPI REST API
├─ SQLite ← 分析引擎
└─ AI Decision Agent ← SQLite 权威上下文
```

核心原则是：

- Statistics are deterministic；
- AI is interpretative；
- Providers are replaceable；
- Frontend is provider-agnostic。

### 9.3 API 能力

数据与系统接口：

- `GET /health`
- `GET /boroughs`
- `GET /boroughs/{borough_id}`
- `GET /indicators/{borough_id}`
- `GET /analysis/{borough_id}`

AI 接口：

- `GET /ai/status`
- `POST /ai/analyze`
- `POST /ai/chat`
- `POST /ai/compare`
- `POST /ai/report`

### 9.4 前后端职责边界

前端不直接：

- 读取 CSV；
- 连接 SQLite；
- 执行 PCA 或 TOPSIS；
- 判断当前 AI Provider。

后端负责：

- 初始化 Schema；
- 查询并返回行政区、指标和分析结果；
- 构建 AI 权威上下文；
- 校验请求及返回结构；
- 选择 Mock 或 Live 模式；
- 隔离模型服务异常；
- 对错误和日志进行脱敏。

## 10. 关键产品与设计决策

### 10.1 为什么以地图为主界面

城市潜力天然具有空间属性。地图比传统表格或 KPI Dashboard 更适合作为行政区发现与选择入口，也能让用户在查看评分前先建立区域位置认知。

### 10.2 为什么不是传统 Dashboard

一次展示全部 33 个行政区、12 项指标和多组评分会形成高认知负担。平台通过“先选择区域，再显示分析工作区”的渐进式信息架构减少首屏噪音。

### 10.3 为什么 AI 不是普通聊天机器人

普通聊天框将所有任务压缩为文字问答，弱化了地图、图表和模型本身的价值。Urban 被设计为上下文分析助手：

- 悬停时预览区域；
- 选择后展示分析进度；
- 完成后概括分数和排名；
- 随后承接追问、比较与报告任务。

### 10.4 为什么点击区域直接开始分析

用户选择行政区本身已经表达了明确意图，因此取消额外的“Run Analysis”按钮，减少重复确认和无意义步骤。

### 10.5 为什么模型结果预计算并存储

- 减少用户等待；
- 避免每次点击重复计算；
- 保证不同会话和不同 AI Provider 使用相同结果；
- 让统计分析与 AI 服务分别测试和维护。

### 10.6 如何平衡专业性与可理解性

- 用地图承担空间选择；
- 用综合评分和排名提供快速结论；
- 用维度卡片、雷达图和贡献度图逐层展开；
- 用指标卡片保留专业细节；
- 用 AI 把统计结果翻译为自然语言；
- 用报告承接正式决策沟通。

### 10.7 为什么支持多 Provider

通过 Strategy Pattern 统一 OpenAI、Qwen 与 DeepSeek，降低单一供应商依赖，也便于在模型效果、成本和地区可用性之间切换，而无需修改前端。

### 10.8 为什么需要 Mock AI

Mock 模式让前端交互、状态流转、双语显示和错误处理可以在没有真实 Key、网络成本或模型波动的情况下开发和测试，是 AI 产品工程化而不是单次 Demo 调用的重要体现。

## 11. 项目难点与解决方案

### 11.1 多源空间数据的统一

**难点**：行政区 GeoJSON、指标表和模型结果来自不同载体，命名差异容易导致关联失败。

**方案**：以官方行政区编码作为稳定 ID；`boroughs` 保存几何引用，指标和分析结果通过外键关联；前端统一通过 ID 请求数据。

### 11.2 AI 解释与数学计算的边界

**难点**：如果直接让 LLM 处理评分，结果可能不可复现、无法验证。

**方案**：建立独立 PCA–TOPSIS 分析引擎，将结果持久化；AI 只解释数据库中的确定性结果。

### 11.3 AI 输出的稳定渲染

**难点**：自由文本难以稳定映射为优势、短板、驱动因素和建议卡片。

**方案**：使用结构化 `AnalysisInsights` Schema，并在后端解析和校验；异常内容统一进入错误处理流程。

### 11.4 地图状态与 AI 状态同步

**难点**：悬停、点击、搜索、加载、完成与失败会同时改变地图和 AI 面板。

**方案**：将 AI Panel 明确建模为 `idle → hover → selected → analyzing → completed` 状态，并让地图点击与搜索选择复用同一分析流程。

### 11.5 数据库路径一致性

**难点**：从项目根目录或 `backend/` 启动时，相对路径可能创建两个不同数据库。

**方案**：相对数据库路径统一基于后端目录解析，并在 FastAPI 启动时记录最终绝对路径。

### 11.6 双语数据与界面一致性

**难点**：界面语言可切换，但行政区、指标 ID、数值和模型结果不能因翻译而失去一致性。

**方案**：只翻译 UI 与指标 Label，保留官方行政区名称、稳定 ID、JSON 字段和数值；新 AI 请求使用当前语言，历史回答不被自动重写。

### 11.7 外部模型错误与密钥安全

**难点**：Provider 异常可能泄露请求细节或 API Key。

**方案**：后端返回通用 502/503 错误；日志记录 Provider、异常类型、状态码和 Request ID，但对 Key 及常见密钥模式进行脱敏。

## 15. 后续规划

### 15.0 相比手工分析的效率变化

平台没有消除数据准备工作：区域 GeoJSON、原始指标采集、清洗和数据质量判断仍需人工完成。它降低的是数据准备完成之后的重复分析成本。

传统方式下，每更换一个地区或数据版本，分析人员需要重新运行 PCA / 综合评价、整理排名和贡献因素、制作地图与图表，再手工组织文字结论。平台搭建后，只需准备符合 Schema 的区域 GeoJSON 和指标表，即可复用统一流程完成导入、计算、可视化、AI 辅助解读和 Markdown 报告。

因此，现阶段最准确的成果口径是：

> 将一次性的手工城市评价流程沉淀为可迁移的分析产品，减少重复建模、制图和报告整理步骤，显著降低更换地区或数据版本后的边际分析时间。

在未做计时对照实验前，不写具体“节省 X% 时间”。

## 16. 关键迭代与 AI 辅助开发判断

### 16.1 最关键的一次需求 / 架构迭代

最关键的迭代是：**从一次性 PCA 空间分析报告，重构为“确定性分析引擎 + 数据库存储 + AI 解释层”的可复用产品架构。**

迭代前，分析结果主要停留在 SPSS、ArcGIS / R 输出和静态报告中；每次更换地区或数据版本，都需要分析人员重新串联计算、制图和结论整理。迭代后：

- 将区域、指标与模型结果统一存入 SQLite；
- 将 PCA 加权 TOPSIS 独立为可重复运行的确定性引擎；
- 将结果通过 FastAPI 提供给地图、图表与 AI；
- 让 AI 只读取权威上下文并负责解释，不参与评分计算；
- 通过结构化输出和多 Provider Strategy 保证前端稳定、模型可替换。

这次迭代同时解决了三个问题：分析流程难复用、专业结果难理解、LLM 直接计算不可信。

### 16.2 AI 辅助开发工具的使用范围

AI 辅助覆盖：

- 产品与技术 specs 的梳理；
- React / TypeScript / MapLibre 前端代码生成与迭代；
- FastAPI、SQLite、Provider 层与测试代码辅助；
- UI 样式调整、报错定位和文档整理；
- 基于权威 Context 的分析报告生成。

### 16.3 本人判断与修改部分

本人承担的核心判断不是“接受 AI 给出的所有代码或建议”，而是：

- 判断功能是否真正服务“城市分析”主流程；
- 决定地图优先而非传统 Dashboard 的信息架构；
- 明确 PCA–TOPSIS 与 LLM 的职责边界；
- 核对指标方向、数据来源、模型结果与行政区关联；
- 运行 Build、测试和真实模型调用，定位并修正实现问题；
- 审核 AI 报告是否把标准化指标误解为现实绝对值；
- 对缺乏文献或数据库依据的建议保留人工判断，不直接作为决策结论。

Westminster 报告中的语义问题正好说明：AI 可以降低解释和报告整理成本，但建议是否可采纳，仍需要结合指标口径、原始数据、规划背景和参考文献由人判断。

## 19. 当前推荐的项目叙事

### 19.1 30 秒版本

UrbanInsight AI 是我把小组时期的伦敦城市生活质量研究进一步产品化的项目。原研究整合 33 个行政区的 12 项经济、社会和生态指标，用 PCA 与空间统计分析区域差异；之后我独立将它重构为 PCA 加权 TOPSIS 分析引擎，并通过 React、MapLibre 和 FastAPI 做成地图优先的平台。AI 不负责计算，而是基于数据库中的真实结果解释优势、短板，支持追问、区域比较和 Markdown 报告。

### 19.2 一分钟版本

这个项目最初是我担任负责人完成的伦敦城市生活质量研究。我们整合 POI、Landsat 遥感、土地利用和政府统计数据，构建 33 个行政区、12 项指标的评价体系，用 PCA 和空间统计分析区域差异。后来我发现静态报告难复用、专业结果也不容易理解，因此在 2026 年独立将它重构为 UrbanInsight AI：以地图作为入口，用 PCA 加权 TOPSIS 引擎生成稳定的评分、排名和贡献度并写入 SQLite，再由受约束的 AI Context 生成解释、优势、短板和建议。系统支持 Qwen、DeepSeek、Mock、多轮追问、区域比较、双语和 Markdown 报告。架构上我刻意把统计计算与 AI 解释分开，提高结果的可信性和可维护性。

## 20. 总结

UrbanInsight AI 的核心创新不是单一算法或单一界面，而是把城市空间数据、综合评价模型、GIS 交互和大语言模型组织为一套可解释的决策分析产品。

它体现了四类能力的结合：

- **分析能力**：指标体系、PCA–TOPSIS、贡献度与区域比较；
- **产品能力**：用户任务、信息架构、AI 状态、渐进式披露与报告闭环；
- **技术能力**：React、TypeScript、MapLibre、FastAPI、SQLite 与多 Provider AI；
- **可信 AI 能力**：权威上下文、计算解释分离、结构化输出、错误兜底与安全配置。

后续所有简历描述和面试材料都应围绕这一完整叙事展开，而不是将项目拆成“数据分析项目”和“后来做的网站”。
